- 把意图路由、视觉预分析、混合检索、生成与证据复核编排为完整业务链，并实现三档可配路由：确定性规则 / 大模型 function-calling / 护栏+大模型混合，59 案例对比显示混合模式在保持 96.6% 准确率的同时减少 58% 的模型调用。

## 面试讲解顺序

### 1. 问题

普通 RAG Demo 只能回答问题，无法处理退款、投诉、安全事故、证据不足和人工接管，也缺少可验证的质量指标。

### 2. 架构选择

先用确定性 Agent Policy 决定动作，再让 RAG 和模型处理适合自动回答的请求。生成后再检查证据，形成前后两道护栏。

### 3. 多模态检索

用户问题可能只说“这个设备”，所以先从图片提取产品和关键词。产品识别不是绝对可信，因此根据置信度选择硬过滤、软加权或忽略，降低错识别导致的检索污染。

### 4. 可靠性

视觉失败不阻断文字检索；模型瞬时错误重试，持续错误熔断；知识证据不足不让模型继续编造，而是创建工单。

### 5. 工程闭环

对话之外还实现工单、反馈、运营摘要、指标、日志、鉴权、限流、健康检查、Docker 和 CI，使系统具备服务形态。

### 6. 质量证明

分别评估代码回归、检索召回、Agent 路由和真实生成。这样能定位失败究竟来自代码、知识检索、策略还是外部模型。

## 高频追问

### 为什么不用大模型做所有意图判断？

退款、安全风险和明确转人工属于高确定性、高风险动作。硬规则可解释、可测试、延迟低；未来可在长尾意图上增加分类模型，但硬规则仍应优先。

### 为什么检索后还要证据复核？

模型可以在空上下文下生成流畅答案。复核引用和上下文数量可以把“无证据回答”转换为人工处理，降低幻觉风险。

### 为什么使用 SQLite？

当前目标是单实例可交付项目，SQLite 简化部署且支持持久化和 WAL。架构明确了水平扩容前迁移 PostgreSQL/Redis 的边界。

### 为什么性能测试使用 Mock 模型？

它隔离外部供应商抖动，测量 API、检索、存储和编排本身。真实模型延迟需要单独测量，不能和本地基线混为一谈。

### 如何继续升级？

优先级依次是共享存储与限流、CRM 工具适配、SSE 流式响应、低分反馈自动采样、真实模型评测扩容和灰度发布。
